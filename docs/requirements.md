# BdayMate — 全栈生日管理平台开发任务书

## 1. 项目背景

你现在是一名资深全栈工程师、产品架构师和 UI/UX 设计师。

请帮助我从零开发一个完整的生日管理 Web 应用。

项目名称：BdayMate

中文名称：生日搭子

产品 Slogan：Never Miss a Special Day.

产品定位：

BdayMate 是一个帮助用户记录重要联系人生日、管理人际关系、查看生日日历，并通过邮件提前提醒用户的个人生日管理工具。

核心目标：

1. 帮助用户记录家人、朋友、同事、客户等重要联系人的生日。
2. 支持公历生日和农历生日。
3. 自动计算生日倒计时和年龄。
4. 通过 SMTP 邮件在生日之前及当天发送提醒。
5. 提供清晰、美观的 Dashboard 和生日日历。
6. 支持标签、分组、备注、祝福语和礼物记录。
7. 用户只能管理自己的联系人，所有数据必须安全隔离。

产品采用现代 SaaS Dashboard 风格，要求 UI 美观、交互流畅、响应式布局，并且是真正可用的完整产品，而不是静态原型。

## 5. 生日计算引擎

这是本项目重点模块。

请单独封装 BirthdayService，不要把生日计算散落在页面组件中。

### 公历处理

- 每年重复。
- 处理 2 月 29 日。
- 出生年份可选。
- 计算下一个生日。
- 计算距离生日天数。
- 计算年龄。
- 处理跨年日期。

默认 2 月 29 日在非闰年按 2 月 28 日处理，同时预留用户自定义策略。

### 农历处理

- 农历日期转公历。
- 公历日期转农历。
- 支持闰月。
- 支持农历出生年份为空。
- 每年重新计算实际对应的公历生日。
- 没有对应闰月的年份必须有明确处理策略。
- 处理春节跨年。
- 测试不同年份的农历生日。

必须建立独立的单元测试。

不允许直接使用简单的公历年份比较来代替农历生日计算。

如果日期转换库存在覆盖范围限制，必须明确提示，不允许返回错误的生日日期。

### 时区处理

使用 IANA 时区标识。

所有持久化的任务时间统一保存 UTC。

生日日期按用户时区计算。

必须避免服务器时区与用户时区不一致导致生日提前或延迟一天。

## 6. SMTP 与定时任务架构

核心要求：

用户关闭网站后，生日提醒依然能够正常执行。

### 环境变量

建立 .env.example：

DATABASE_URL=
DIRECT_URL=

BETTER_AUTH_SECRET=
BETTER_AUTH_URL=

NEXT_PUBLIC_APP_URL=

SMTP_HOST=
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=
SMTP_PASS=
SMTP_FROM=
SMTP_FROM_NAME=BdayMate

CRON_SECRET=

具体数据库连接配置和 Prisma Adapter 按照当前版本官方要求设置。

### 邮件发送

统一实现：

- createTransporter
- verifySMTPConnection
- sendEmail
- sendVerificationEmail
- sendPasswordResetEmail
- sendBirthdayReminderEmail
- sendTestEmail

要求：

- 复用 SMTP Transporter。
- 正确配置 TLS。
- 生产环境验证服务器证书。
- 不在前端暴露 SMTP 账号和密码。
- 完整捕获错误。
- 发送失败保存日志。
- 支持重试。

### 邮件队列

EmailQueue 应具有：

- id
- userId
- recipient
- template
- subject
- payload
- scheduledAt
- status
- attemptCount
- lastError
- dedupeKey
- sentAt
- createdAt
- updatedAt

状态：

PENDING
PROCESSING
SENT
FAILED

需要通过数据库事务或原子领取机制，避免多个任务执行器重复处理同一条任务。

相同提醒不能重复发送。

### 生日提醒任务

采用两阶段调度：

第一阶段：生成未来 30～45 天的提醒任务。

第二阶段：定时 Worker 检查已经到达执行时间的任务，通过 SMTP 发送。

联系人生日修改、提醒配置修改时，需要重新计算未发送的任务。

重试采用指数退避策略，并且有最大重试次数。

实现安全 Cron 接口：

POST /api/cron/generate-reminders
POST /api/cron/process-email-queue

具体是否拆分为两个端点可以根据工程设计优化。

所有 Cron 接口必须验证 CRON_SECRET。

不能依赖浏览器打开页面触发提醒。

需要提供本地测试命令，能够手动执行任务生成和队列处理。

## 8. 工程架构和代码规范

采用分层设计：

app：
负责页面路由和布局。

components：
负责可复用 UI 组件。

features：
按照业务模块管理前端功能。

services：
负责业务逻辑、数据库交互和服务端流程。

lib：
负责基础设施、公共工具和数据库连接。

stores：
负责 Zustand 客户端状态。

emails：
负责邮件模板。

tests：
负责测试代码。

必须遵守：

1. TypeScript 严格模式。
2. 避免 any。
3. 业务组件不能直接操作 Prisma。
4. 数据库操作必须经过服务端。
5. 服务端敏感逻辑必须使用 server-only。
6. 不在 React Server Components 中直接操作 Zustand Store。
7. 服务端必须重新校验所有客户端传入数据。
8. 每个业务接口都必须验证登录状态和数据所有权。
9. 使用合理的错误处理和日志。
10. 不允许将密钥、密码和 Token 提交到 Git。
11. 不允许使用大量重复代码。
12. 不允许用 Mock 数据冒充已经实现的功能。
13. 不允许随意删除已有业务逻辑或重写无关模块。
14. 核心功能必须具有自动化测试。
